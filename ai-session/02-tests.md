## Preguntas que el MAP no cubre — no las inventé

1. **`InvalidPhoneNumberError` vs `InvalidLeadError`.** §4 escribe `entrada válida (PhoneNumber, name) → InvalidPhoneNumberError / InvalidLeadError`. La barra no ordena el par. Si llegan teléfono malformado **y** nombre vacío a la vez, ¿cuál gana? **No hay test para ese par.**
2. **¿El caso de duplicado tiene la misma garantía de "no se consulta la ocupación"?** §4 lo dice literal sólo para misma-etapa-llena. Para duplicado dice quién gana, pero no si `findByStage` llega a llamarse. Afirmo el error, **no** afirmo la ausencia de la llamada — al revés que en el caso de mover, donde sí lo afirmo porque está escrito.
3. **¿Contra qué firma del puerto quieres los tests?** La actual (`string`) o la de §7 (`PhoneNumber`). Escribí contra la actual porque es la que compila.
4. **¿`AddLeadToFunnel` construye el `Lead` antes o después del chequeo de duplicado?** §2 pone la validación del nombre dentro de `Lead`, y §4 la pone en el primer paso del pipeline. Ambas cosas sólo son ciertas a la vez si el caso de uso hace `new Lead(...)` antes de consultar el repositorio. Mi test *"prefers the empty-name error over the duplicate error"* codifica esa lectura; si prefieres validar el nombre suelto en el caso de uso, la regla queda duplicada en dos sitios y ese test hay que revisarlo.
5. **¿El nombre se guarda tal cual o normalizado?** Relacionado con la observación 3. Ningún test lo fija.
6. **¿`findByStage` garantiza algún orden?** §10/Q3 reconoce que no hay orden ni paginación. Mis tests del repositorio evitan depender de ello (comparo listas de un elemento, o sólo `length`). Si quieres que el orden de inserción sea contrato, hace falta un test y una línea en el MAP.
7. **¿`DuplicateLeadError` recibe el teléfono canónico o el input crudo?** §6 lo dice explícitamente sólo para `LeadNotFoundError` (*"El caso de uso pasa `phone.value`"*). Por el criterio de firmas de §3 (*"sobre una entidad: su id"*) y por §1 (la identidad **es** la forma canónica) parece resuelto, pero no está escrito. No afirmo el contenido del mensaje en ningún test de esos dos errores.
